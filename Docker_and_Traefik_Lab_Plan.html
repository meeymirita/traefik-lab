0. Введение в Docker: с нуля #

Если вы никогда раньше не запускали docker run — начните здесь. Дальше в лабе постоянно встречаются слова «контейнер», «образ», «сеть», «volume» так, будто вы уже с ними знакомы. Это нормально: без этого раздела разделы 1–9 действительно читаются как набор незнакомых терминов. После этого раздела вернитесь к разделу 1 — он станет понятнее.

0.1 Проблема, которую решает Docker

Классическая боль: «у меня на компьютере работает, а на сервере — нет». Причина обычно в окружении: другая версия PHP/Node/Python, не та версия библиотеки, забытая переменная окружения. Docker решает это так: вместо того чтобы устанавливать приложение прямо на компьютер (и зависеть от того, что на нём уже стоит), приложение упаковывается вместе со всем, что ему нужно для работы — конкретной версией языка, библиотеками, настройками — в один переносимый пакет. Этот пакет одинаково запускается и у вас на ноутбуке, и на сервере, и у коллеги.

💡 Контейнер — это не виртуальная машина

Виртуальная машина (VM) эмулирует целый компьютер: у неё своё ядро операционной системы, она «весит» гигабайты и стартует минуту. Контейнер — это изолированный процесс, который использует ядро операционной системы хоста (вашего компьютера), но видит только свою файловую систему и свою сеть — как будто он один в отдельной коробке. Из-за этого контейнер весит мегабайты, а не гигабайты, и стартует за секунды, а не за минуту. Изоляция чуть слабее, чем у полноценной VM, но для 95% задач разработки и деплоя этого более чем достаточно.

0.2 Образ (image) и контейнер (container) — в чём разница

Это самая частая путаница у новичков, поэтому разберём отдельно.

Из одного образа можно запустить сколько угодно контейнеров одновременно — точно так же, как из одного класса можно создать много объектов. Именно так работает масштабирование в шаге 2.4: три контейнера API — это три независимых процесса из одного и того же образа.

0.3 Основные команды — шпаргалка

# посмотреть образ и скачать/собрать его
docker pull nginx                    # скачать готовый образ с Docker Hub
docker build -t myapp .              # собрать свой образ из Dockerfile в текущей папке

# запустить контейнер
docker run -d --name web -p 8080:80 nginx
#            │        │      │
#            │        │      └─ проброс порта: локальный:контейнерный
#            │        └─ имя контейнера, чтобы не запоминать ID
#            └─ detached: в фоне, не занимая терминал

# посмотреть, что вообще происходит
docker ps                            # список запущенных контейнеров
docker ps -a                         # + остановленные
docker logs -f web                   # логи контейнера в реальном времени
docker exec -it web sh               # зайти "внутрь" контейнера терминалом

# остановить и убрать
docker stop web && docker rm web
Зачем это знать до Traefik: когда в разделе 9 что-то не заработает, первое, что вы будете делать — docker compose logs -f traefik и docker ps, чтобы увидеть, что контейнер вообще запустился и не падает в перезапуск.

0.4 Docker Compose — зачем он, если уже есть docker run

В этой лабе не один контейнер, а несколько: Traefik, API, frontend, база данных, Adminer — и все они должны видеть друг друга и знать, кто где. Запускать каждый отдельной длинной командой docker run с десятком флагов — неудобно и легко ошибиться. Docker Compose — это способ описать все контейнеры, их сети и тома одним файлом docker-compose.yml, а затем поднять всё разом одной командой.

docker compose up -d       # поднять всё, что описано в docker-compose.yml, в фоне
docker compose ps          # какие сервисы подняты
docker compose logs -f     # логи всех сервисов сразу
docker compose down        # остановить и удалить все контейнеры проекта

В файле каждый контейнер называется не «контейнером», а сервисом (service) — потому что Compose может поднять несколько одинаковых контейнеров под одним сервисом (это и есть масштабирование из шага 2.4).

0.5 Сеть (network) — как контейнеры находят друг друга

По умолчанию контейнеры изолированы друг от друга. Docker Compose создаёт для проекта общую сеть, и все сервисы, подключённые к ней, могут обращаться друг к другу по имени сервиса, как по доменному имени — Docker сам поднимает внутренний DNS. Если в docker-compose.yml есть сервис db, то из сервиса api к нему можно обратиться просто как db:5432, без всякого IP-адреса — Docker сам его подставит.

ЭТО КЛЮЧЕВАЯ ИДЕЯ ДЛЯ ВСЕЙ ЛАБЫ

Traefik работает ровно так же: когда в шаге 2.1 вы увидите traefik.http.services.api.loadbalancer.server.port=3000 — это именно порт внутри сети Docker, куда Traefik стучится по внутреннему имени сервиса api, а не порт, открытый наружу на вашем компьютере. Наружу в итоге открыт только сам Traefik (порты 80/443), а всё остальное общается друг с другом только внутри этой внутренней сети — снаружи эти адреса вообще не видны.

0.6 Volume — почему данные не пропадают при перезапуске контейнера

Контейнер по умолчанию «одноразовый»: если его удалить и создать заново из того же образа, всё, что было записано внутри (например, данные в базе), пропадёт. Volume — это папка, которая живёт вне контейнера, на хосте, и «подключается» внутрь него. Контейнер можно пересоздавать сколько угодно раз — volume и данные в нём останутся. В этой лабе volume используется для PostgreSQL (шаг 2.3), чтобы заказы и таблицы не терялись при каждом docker compose down.

0.7 Порты: проброс наружу vs общение внутри сети

Флаг -p 8080:80 (или в compose — ports: ["8080:80"]) означает «сделать порт 80 внутри контейнера доступным снаружи как порт 8080 на моей машине». Это единственный способ достучаться до контейнера извне Docker-сети — с вашего браузера. В этой лабе такой проброс есть только у одного контейнера — Traefik (порты 80 и 443, шаг 1.3). Все остальные сервисы (API, frontend, БД) портов наружу не пробрасывают вообще — до них можно достучаться только через внутреннюю сеть, то есть только через Traefik. Это и есть смысл reverse proxy: один открытый вход вместо десятка.

0.8 Podman — то же самое, но без постоянного демона

Podman — альтернатива Docker с почти идентичными командами (podman run, podman ps, podman compose). Главное отличие: Docker всегда держит в фоне единый демон-процесс с правами root, который управляет всеми контейнерами, а Podman запускает каждый контейнер как обычный процесс без постоянного демона и умеет работать полностью без root (rootless) — это чуть безопаснее. Для наших целей разница станет заметна только в одном месте — сокете для Traefik (шаг 1.6), всё остальное в лабе работает одинаково что на Docker, что на Podman.

1. Разбор задачи: зачем именно Traefik #

СОВСЕМ ПРОСТЫМИ СЛОВАМИ

Reverse proxy — это «секретарь на входе»: клиент стучится не напрямую к нужному сервису, а к секретарю (Traefik), и секретарь по адресу запроса (какой домен, какой путь) решает, к какому именно сервису его провести. Сервисы при этом вообще не видны снаружи напрямую — только через этого секретаря. Именно поэтому в разделе 0.7 наружу открыт только порт самого Traefik, а не портов API/frontend/БД.

Задача — поднять несколько сервисов (API, frontend, админку БД) за одним входом на 80/443 порту, без ручного прописывания nginx.conf под каждый новый контейнер. Классический nginx как reverse proxy тоже умеет маршрутизацию, но конфиг нужно писать руками и перезагружать вручную. Traefik1 читает конфигурацию маршрутов прямо из label'ов контейнеров и обновляет её на лету — контейнер запустился → правило появилось, контейнер остановился → правило исчезло.

💡 Почему не просто «пробросить порты наружу»

Наивный вариант — каждому сервису свой порт: API на :3000, frontend на :8080, Adminer на :8081. Работает, но: (1) в проде вы не можете открыть десяток портов клиенту — только 80/443; (2) TLS2 пришлось бы настраивать в каждом сервисе отдельно; (3) добавление второй реплики API ломает схему «порт = сервис». Traefik решает всё это одним слоем: один вход, маршрутизация по домену/пути, TLS и балансировка централизованно.

2. Как Traefik устроен внутри #

Traefik строит конфигурацию из двух слоёв: статическая конфигурация3 (что нельзя менять без рестарта: какие порты слушать, какие providers включены) и динамическая конфигурация4 (роутеры, middlewares, TLS-настройки — обновляется на лету).

ПРОСТЫМИ СЛОВАМИ ПРО ТАБЛИЦУ НИЖЕ

Если коротко: запрос сначала попадает в «дверь» (EntryPoint), Traefik узнаёт, какие вообще есть правила (Provider), сверяет запрос с правилами (Router), пропускает через охрану/фильтры (Middleware) и в конце отправляет в нужный контейнер (Service). Все пять терминов ниже — это буквально пять слов, в которых чаще всего путаются на старте; возвращайтесь к этой таблице каждый раз, когда встретите незнакомое слово из этого списка.

СущностьЧто делаетАналогия
EntryPoint5слушающий порт (web=80, websecure=443)«входная дверь»
Provider6источник конфигурации: Docker labels, файл, Consul, Kubernetes CRD«откуда брать правила»
Router7правило «если Host/Path такой — веди сюда»маршрут в роутере Wi-Fi
Middleware8обработка запроса до сервиса: auth, rate-limit, headers, StripPrefixохрана на входе
Service9куда реально отправить запрос: один или несколько backend'ов + алгоритм балансировкисам ресторан за дверью
Клиент → EntryPoint (:80/:443) → Router (matches Host/Path) → [Middleware chain] → Service → контейнер(ы)
🔬 Под капотом: почему providers два вида, и что если их несколько сразу

Docker provider — самый удобный для compose-стека: правила лежат прямо в labels: нужного сервиса, рядом с его описанием. Но у него нет доступа к тому, что не запущено в Docker/Podman — например, к внешнему legacy-серверу на другой машине. Для этого есть file provider: статический (или динамически перечитываемый) YAML/TOML файл, куда роутер и service прописываются руками с конкретным IP:порт вместо label'а.

Traefik умеет объединять несколько providers одновременно — их конфигурации мержатся. На практике это значит, что часть маршрутов может жить в labels, а часть (например, глобальные middlewares вроде secure-headers) — в общем файле dynamic/middlewares.yml, чтобы не копировать один и тот же блок в каждый сервис.

5. Service Discovery через labels #

Traefik подключается к Docker-сокету (/var/run/docker.sock) в режиме только чтения и подписывается на события: контейнер запущен/остановлен/изменён. У каждого контейнера, который хочет получить маршрут, в labels: описывается мини-конфигурация роутера прямо в compose-файле.

services:
  whoami:
    image: traefik/whoami
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.whoami.rule=Host(`whoami.localhost`)"
      - "traefik.http.routers.whoami.entrypoints=web"
      - "traefik.http.services.whoami.loadbalancer.server.port=80"
💡 exposedByDefault=false — обязательная настройка

По умолчанию Traefik готов раздать маршрут любому контейнеру в сети, даже без единого label — просто по первому открытому порту. В проекте с десятком контейнеров это создаёт случайные, никем не запланированные роуты. Поэтому в статической конфигурации (шаг 1.2) выставляется providers.docker.exposedByDefault: false, и каждый сервис явно включается через traefik.enable=true.

🔬 Под капотом: как имя роутера попадает в label, и что будет при коллизии

Формат label — traefik.<http|tcp>.<routers|services|middlewares>.<имя>.<свойство>=значение. Имя (whoami в примере) — произвольная строка, но должно быть уникальным во всей топологии: если два разных сервиса объявят роутер с одинаковым именем, Traefik подхватит один из них по правилам приоритета конфигурации провайдеров и залогирует конфликт — вы получите «работает, но не тот сервис», что отлаживать неприятно. Поэтому на практике имя роутера обычно = имя compose-сервиса.

Что если контейнер слушает нестандартный порт. loadbalancer.server.port — это порт внутри контейнера, а не то, что видно снаружи (порты наружу вообще не публикуются — весь трафик идёт через внутреннюю Docker-сеть). Забытый или неверный port — самая частая причина «502 Bad Gateway» у новичков.

6. Сценарий: путь запроса от браузера до контейнера #

GET https://api.localhost/users/42
  1. Запрос приходит на EntryPoint websecure (:443). TLS terminates здесь — контейнер API про HTTPS не знает вообще.
  2. Traefik ищет среди всех роутеров тот, чей rule совпадает: Host(`api.localhost`). Если совпало несколько правил — побеждает более специфичное (длиннее по правилу), либо явный priority.
  3. Запрос проходит цепочку middlewares роутера по порядку: например, ratelimit → headers (раздел 7).
  4. Router передаёт запрос в service: если реплик несколько — балансировщик (round robin по умолчанию) выбирает живую, здоровую реплику по последнему известному healthcheck.
  5. Ответ идёт обратно тем же путём; Traefik добавляет заголовки вроде X-Forwarded-For, чтобы API знал реальный IP клиента.

💡 Балансировка — это не только round robin

По умолчанию Service с несколькими серверами использует round robin10. Для canary-деплоя (шаг 3.3) вместо этого объявляют два отдельных service (v1 и v2) и оборачивают их в weighted service с процентным распределением трафика — например, 90% на стабильную версию, 10% на новую. Health check11 при этом работает независимо от алгоритма: нездоровая реплика просто исключается из ротации, какой бы алгоритм ни стоял.

🔬 Под капотом: почему порядок middlewares в цепочке важен

Middlewares выполняются строго в том порядке, в котором перечислены в router.middlewares. Если поставить headers (добавляет CORS) после ratelimit — заблокированный по лимиту запрос получит ответ 429 без CORS-заголовков, и браузер покажет непонятную CORS-ошибку вместо настоящей причины (rate limit). Правило: middlewares, которые должны сработать на «отказных» ответах тоже — ставить первыми.

🔬 Под капотом: почему сокет монтируется read-only, и что это НЕ делает безопасным

:ro запрещает Traefik писать в сокет напрямую средствами файловой системы, но сам Docker API, доступный через сокет, всё равно позволяет создавать/удалять контейнеры, читать секреты в переменных окружения других контейнеров и так далее — доступ к docker.sock фактически эквивалентен root на хосте. Флаг :ro — это гигиена, а не полноценная изоляция; для честной изоляции в проде используют docker-socket-proxy — прокси, которое отдаёт только тот минимум Docker API, что нужен Traefik (листинг контейнеров и событий), и ничего больше.

11. Глоссарий терминов #

1. Traefik ↩ — reverse proxy и load balancer с автоматическим обнаружением сервисов (Docker, Kubernetes, Consul и др.).

2. TLS ↩ — протокол шифрования соединения (то, что даёт HTTPS вместо HTTP).

3. Статическая конфигурация ↩ — настройки, задаваемые при старте Traefik (файл/CLI/env): порты, providers, дашборд. Требует рестарта при изменении.

4. Динамическая конфигурация ↩ — роутеры, middlewares, сервисы, TLS-сертификаты. Обновляется на лету без рестарта Traefik.

5. EntryPoint ↩ — точка входа: сетевой порт, который слушает Traefik (например, web=80).

6. Provider ↩ — источник динамической конфигурации: Docker labels, файл, Kubernetes CRD, Consul и т.д.

7. Router ↩ — правило сопоставления входящего запроса (Host/Path/заголовки) с конкретным сервисом.

8. Middleware ↩ — обработчик, изменяющий запрос или ответ до/после доставки в сервис (auth, rate limit, заголовки и т.д.).

9. Service ↩ — описание одного или нескольких backend-серверов и алгоритма распределения трафика между ними.

10. Round robin ↩ — алгоритм балансировки, по очереди отправляющий запросы каждому серверу списка.

11. Health check ↩ — периодическая проверка живости backend'а; нездоровые серверы временно исключаются из балансировки.

12. ForwardAuth ↩ — middleware, делегирующее решение об авторизации внешнему HTTP-сервису (например, SSO) перед пропуском запроса дальше.

14.5 TLS: сразу продакшен, но сначала — staging-проверка

У вас реальный домен, доступный из интернета, — HTTP-01 challenge (раздел 8) заработает по-настоящему. Но всё равно сначала прогоните staging-резолвер (шаг 3.2) один раз целиком, чтобы убедиться, что DNS, файрвол и labels настроены верно — и только потом переключайтесь на боевой CA. Причина та же, что и в разделе 8: у продакшен Let's Encrypt жёсткий лимит (5 неудачных попыток в час на домен), и опечатку в label лучше словить на staging, где лимит не жалко потратить.

api:
  dashboard: true

  web:
    address: ":80"
    http:
      redirections:
        entryPoint:
          to: websecure
          scheme: https
  websecure:
    address: ":443"

providers:
  docker:
    endpoint: "unix:///var/run/docker.sock"
    exposedByDefault: false
    network: traefik-public
  file:
    directory: /etc/traefik/dynamic
    watch: true

certificatesResolvers:
  letsencrypt:
    acme:
      email: you@example.com
      storage: /etc/traefik/acme/acme.json
      # ШАГ 1: сначала проверяем на staging
      caServer: "https://acme-staging-v02.api.letsencrypt.org/directory"
      httpChallenge:
        entryPoint: web
# .env на сервере — реальный email, не в traefik.yml
ACME_EMAIL=ваш-настоящий-email@meeymirita.ru

И, как в шаге 3.2, переопределяем его через command: - "--certificatesresolvers.letsencrypt.acme.email=${ACME_EMAIL}" в сервисе traefik — реальный адрес остаётся только в .env на сервере, а не в закоммиченном traefik.yml.

Зачем блок web.http.redirections: на реальном сайте нельзя оставлять рабочий HTTP рядом с HTTPS — пользователь, зашедший по старой ссылке на http://meeymirita.ru, должен автоматически попасть на https://. Эта настройка EntryPoint'а web делает редирект глобально, для всех роутеров сразу, без отдельного middleware на каждом сервисе.

      - "traefik.http.services.frontend.loadbalancer.server.port=80"

По тому же образцу переносите остальные роутеры (api, dashboard→panel, adminer→db) из таблицы 14.4: меняете rule на реальный домен, добавляете entrypoints=websecure и tls.certresolver=letsencrypt, отдельный роутер на entrypoints=web для них больше не нужен — редирект теперь глобальный (14.5).

14.7 Порядок первого запуска на сервере

  1. DNS-записи добавлены, nslookup для всех четырёх поддоменов отдаёт 45.10.166.23 (14.2).
  2. Файрвол пропускает 80/443 (14.3).
  3. Сначала поднимите всё без TLS — только с entrypoints=web и реальными доменами вместо *.localhost — и проверьте curl http://api.meeymirita.ru/health с самого сервера и снаружи.
  4. Добавьте блок certificatesResolvers со staging-CA (14.5), переключите роутеры на websecure + tls.certresolver, поднимите заново, проверьте в браузере (будет предупреждение о недоверенном сертификате — это ожидаемо для staging).
  5. Уберите строку caServer целиком (без неё Traefik по умолчанию использует боевой Let's Encrypt), пересоздайте контейнер Traefik, чтобы staging-сертификаты в acme.json не мешали — проще всего один раз очистить файл (echo '{}' > traefik/acme/acme.json) и поднять заново.
