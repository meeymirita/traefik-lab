Это сессия без новой теории: ты сама дорабатываешь итоговый стек из шага 10.5, используя всё пройденное.

**Задача.** Хозяйка кофейни договорилась с поставщиками: они будут присылать **автоматические заказы** через **партнёрский API**. Нужно выставить его наружу так, чтобы им могли пользоваться только поставщики с клиентскими сертификатами, чтобы один поставщик не мог «завалить» остальных запросами, чтобы новую версию API можно было выкатывать без остановки — и чтобы всё это было видно в метриках и журналах. **Код API и сайта менять нельзя**, обычный сайт и админка продолжают работать как раньше.

**A. Партнёрский сервис `partners`**

1. Новый сервис на готовом образе API (`coffeeshop-api`, **без** изменений кода), две копии, доступен по адресу `https://partners.shop.localhost`; путь `/api` у приложения **не** используется: оно получает запросы в корень.
2. Включена проверка здоровья: больная копия исключается из ротации.
3. Версия приложения задаётся переменной `APP_VERSION` (так видно, какая версия ответила на `/info`).

**B. Доступ и защита**

1. Адрес `partners.shop.localhost` работает **только по HTTPS**, минимальная версия TLS — 1.3; HTTP перенаправляется.
2. Вход **только по клиентскому сертификату** (mTLS) от собственного CA партнёров (как в шаге 7.6); без сертификата соединение не устанавливается.
3. **Ограничение запросов — на каждого партнёра отдельно**: 5 запросов в секунду, всплеск до 10; партнёр определяется по заголовку `X-Api-Key`. Превышение — `429`.
4. Для партнёрской зоны **повторы (`retry`) разрешены только для `GET`**; для `POST` повторов нет. Создание заказа (`POST /orders`) безопасно при повторах со стороны клиента (используется `Idempotency-Key`, который API уже поддерживает).
5. Если партнёрский сервис отвечает ошибками `5xx` чаще, чем в половине запросов, срабатывает **предохранитель** (`circuitBreaker`), а клиенты получают быстрый `503`.
6. Заголовок `X-Forwarded-For` от посторонних **не принимается**: во входе нет доверенных адресов, кроме тех, что ты явно перечислила и обосновала в README.

**C. Выкатка новой версии без простоя**

1. Рядом с версией `v1` может работать версия `v2` (тот же образ с `APP_VERSION=v2`). Доли трафика между ними задаются **весами** в файловой конфигурации и меняются **без перезапуска Traefik**.
2. Скрипт `rollout.sh` переводит трафик ступенями `90/10 → 50/50 → 0/100`. На каждой ступени он ждёт 15 секунд, **запрашивает у Prometheus долю ответов `5xx`** и, если она выше 5%, **автоматически возвращает `100/0`** и завершается с ненулевым кодом.
3. Дополнительно новая версия получает **зеркальный** трафик (копии 20% запросов `GET`, ответы отбрасываются) на время, пока вес `v2` равен нулю.

**D. Наблюдаемость**

1. Журнал доступа в формате JSON, содержит идентификатор запроса из `X-Request-Id`; **записываются только** ошибки (`4xx`–`5xx`) и запросы медленнее 300 мс.
2. Метрики Prometheus включены; Prometheus и Grafana подключены к стеку; в Grafana есть дашборд RED по партнёрскому сервису.
3. Файл правил Prometheus с оповещением «доля `5xx` у партнёрского сервиса выше 5% в течение минуты». Файл проходит проверку `promtool check rules`.
4. Prometheus и Grafana доступны на адресе `ops.shop.localhost`; доступ **только с адресов частных сетей** и **по паролю** (оба условия сразу).

**E. Compose и окружения**

1. Один файл Compose на проект, без цепочки `COMPOSE_FILE`; ни одного секрета в файлах; в репозитории — `.env.example` и `.gitignore`.
2. Весь стек поднимается **одной командой** (`./up.sh`) на пустой машине и останавливается одной (`./down.sh`). Скрипт сам создаёт сертификаты (серверный и клиентский CA партнёров) и пароль.

**F. Проверки**

1. `smoke.sh` дополнен проверками: без клиентского сертификата соединение не устанавливается; с сертификатом — `200`; седьмой запрос в течение секунды с одним ключом получает `429`, а с другим ключом проходит; подделка `X-Forwarded-For` не меняет решения; админка мониторинга без пароля — `401`.
2. Проверка выкатки: `rollout.sh` при «больной» новой версии (например, `POST /sick` на копиях `v2`) возвращает трафик на `v1`.
3. `smoke.sh` печатает «SMOKE: всё в порядке», `docker compose config -q` проходит для всех файлов.

**G. Документация**

1. `README.md`: схема стека, как выпустить клиентский сертификат новому партнёру и как его отозвать, как откатить выкатку вручную, как найти один запрос по `X-Request-Id`, что делать при `502`, `503`, `504`, `429`.

**Критерии приёмки (самопроверка).** Когда ты закончишь, каждая строка таблицы должна выполняться:

| Проверка | Ожидаемый результат |
|---|---|
| `curl http://partners.shop.localhost/` | `301` на `https://` |
| `curl https://partners.shop.localhost/info` (без сертификата) | соединение не устанавливается (`curl` код 56 или 35) |
| то же с клиентским сертификатом | `200`, `version` совпадает с `APP_VERSION` |
| 7 запросов за секунду с `X-Api-Key: A` | первые около 10 — `200`, затем `429` |
| тот же момент с `X-Api-Key: B` | `200` |
| `POST /orders?drop=after` с `--retry 3` и `Idempotency-Key` | в таблице `orders` одна новая строка |
| `X-Forwarded-For: 1.2.3.4` в запросе | в ответе `/info` адреса `1.2.3.4` нет |
| `./rollout.sh` при здоровой `v2` | заканчивается на `0/100`, код `0` |
| `./rollout.sh` при больной `v2` | возвращается `100/0`, код не `0` |
| `ops.shop.localhost` без пароля | `401` |
| `promtool check rules` | `SUCCESS` |
| `./smoke.sh` | «SMOKE: всё в порядке» |

**Чего не требуется:** красивых дашбордов, настоящих доменов, Let’s Encrypt (локальных сертификатов достаточно), аутентификации партнёров сверх сертификата и ключа, развёртывания на сервер.

**Порядок работы (подсказка, не решение):** сначала добавь партнёрский сервис и убедись, что он отвечает в обход защиты; потом TLS и mTLS; потом лимиты по ключу; потом ретраи и предохранитель; потом метрики и журнал; потом выкатка со скриптом; в конце проверки и README. После **каждого** шага смотри дашборд Traefik (роутеры, сервисы, middlewares), запускай `./smoke.sh` и `./diagnose.sh` из шага 10.4 на новых адресах. Если что-то не работает, иди по дереву вопросов из шага 10.4: код ответа → роутер → сервис → журнал.

### result
Здесь нет запуска: это задание для самостоятельной работы. Когда закончишь, пройди таблицу приёмки и ответь на вопросы ниже. **Решения в лабе нет — и это нормально:** ты проверяешь себя сама, а не сверяешься с чужим файлом. Если хочешь получить разбор своей работы, пришли свою папку `final/`.

### why
Это та самая работа, ради которой писалась лаба: на входе — заказ на человеческом языке, на выходе — стек, который можно запустить одной командой, проверить скриптом и объяснить любому коллеге. Всё, что ты сделала здесь, — реальные задачи для любого сервиса за reverse proxy: партнёрский доступ, лимиты, выкатка без простоя, наблюдаемость. Если справилась — ты готова к Kubernetes: там те же идеи называются Ingress, Gateway API и Service Mesh.
